# Product Design Taste

> A reusable agent skill for building and reviewing product UIs that feel **easy to use and not ugly** — and don't look like AI slop.
>
> 一个可复用的 Agent 技能：把「产品设计品味」变成可执行的主流程审查、文案精修、数字校验、克制视觉与验收标准。

## 这是什么

大多数「让 AI 把界面做好看」的尝试都会失败，原因是把审美当成了装饰问题。这个技能换了一个起点：

**解决问题 > 易于使用 > 更好看**

设计是锦上添花，不是产品成败的决定因素。所以技能的执行顺序是固定的：先确认普通用户能独立走完主任务，再处理文案、数字、层级和视觉；任何视觉改动都要能回答「它解决了哪个用户问题」。

技能不产出虚无的「品味分」，而是要求每条问题都带证据：

```
证据（代码路径/截图区域/复现步骤） → 用户影响 → 最小修复 → 验收条件
```

并按影响排序：**P0** 阻断任务或数据/安全风险 → **P1** 高频摩擦与可访问性 → **P2** 一致性与视觉噪音。

## 能力范围

| 场景 | 技能行为 |
| --- | --- |
| 新产品 / 新界面 | 明确主任务与成功信号，定义信息结构、状态和设计变量后实现 |
| 现有代码 + 要求修改 | 先读懂组件、样式、路由、数据与测试，再做最小改动，不顺手重写架构 |
| 现有代码 + 只审查 | 输出带代码行号的问题表，不改文件 |
| 截图 / 原型 | 只评审可见的布局、层级、文案与状态线索，不宣称交互与响应式已验证 |
| 「改了很多版还是不对」 | 给出三个**结构上**有差异的方向并推荐一个，等你选定再深入 |

**不覆盖：** 纯后端任务、品牌插画与 Logo 生成、替代真实用户研究。

## 11 条设计原则

技能的核心检查清单来自一位前端产品工程师在 X 上分享的实战经验，并补充了工程化验收标准。

| # | 原则 | 关键要求 |
| --- | --- | --- |
| 1 | 让不懂技术的普通用户走通主流程 | 入口可发现、按钮说明动作、等待有反馈、失败可恢复且不丢输入 |
| 2 | 文案像母语者说话 | 统一术语与动词，按钮写真实动作，错误提示说明原因与恢复方式 |
| 3 | 不重复解释已经表达清楚的事 | 删除冗余帮助文字，但保留费用、隐私、风险、单位与可访问名称 |
| 4 | 数字必须说明它指什么 | 时间范围、口径、单位、币种、精度、缺失值与零的区分 |
| 5 | 不重复确认用户已选择的普通操作 | 不可逆动作才二次确认，用克制的危险样式而非满屏红色 |
| 6 | 每页一种主强调色 | 默认暖灰中性色，避开旧式后台亮蓝与无理由的橙/陶土色 |
| 7 | 字号尽量少 | 默认不超过四种；行高、字距、段距反复调，满足 WCAG AA 对比度 |
| 8 | 克制特殊排版与行动词 | 斜体/等宽/全大写各有明确用途；同一动作全产品用同一动词 |
| 9 | 组件一致、页面扁平 | 消除卡片套卡片与堆叠阴影；同心圆角 `inner = outer - padding` |
| 10 | 按最长译文布局 | 优先换行、弹性布局与语义等价改写，不缩字号、不截断关键文案 |
| 11 | 多轮不满意就给三个方向 | 固定视口/主题/语言/数据做前后对比，选定后只沿一个方向精修 |

## 技能如何避免「用力过猛」

原帖的审美偏好被当作**默认值**，不是普遍真理。技能明确要求在这些情况下让步：

- **品牌优先**：已有品牌色、深色主题、既有设计系统不被默认风格覆盖。
- **语义色不算装饰**：错误/成功/警告、图表分类色，以及中文金融界面的**涨红跌绿**，不为单色审美牺牲。
- **安全优先**：支付、提权、敏感分享、批量与不可逆操作保留必要确认，即使理论上可退款。
- **数据优先**：不为了「整数好看」损失真实精度，不把前端美化当数据校验。
- **无障碍优先**：对比度、焦点可见性、键盘操作、图标可访问名称不可为了简洁删除。
- **诚实边界**：截图不能证明交互通过；构建通过不等于体验达标；未验证项必须标注。

## 安装

技能就是一个文件夹：一个 `SKILL.md` 加按需加载的 `references/`。任选一种方式。

### 方式一：复制到用户级技能目录（推荐，跨项目可用）

```bash
git clone https://github.com/YoungXu06/product-design-taste.git
mkdir -p ~/.workbuddy/skills
cp -R product-design-taste ~/.workbuddy/skills/product-design-taste
```

安装后目录应为：

```
~/.workbuddy/skills/product-design-taste/
├── SKILL.md
└── references/
    ├── design-checklist.md
    └── acceptance-and-output.md
```

### 方式二：安装为项目级技能（团队共享）

```bash
mkdir -p .workbuddy/skills
cp -R product-design-taste .workbuddy/skills/product-design-taste
```

提交到仓库后，所有协作者都能使用。

### 方式三：用打包文件安装

```bash
# 用 skill-creator 的打包脚本生成分发包
python3 scripts/package_skill.py product-design-taste .
```

解压 `product-design-taste.zip` 后放到上述任一目录。压缩包结构与源码一致，可直接校验；适合分发给不熟悉 git 的同事。

### 方式四：其他 Agent / CLI 工具

`SKILL.md` 是纯 Markdown。Claude Code、Cursor、Codex 等工具可直接把 `SKILL.md` 内容作为项目规则或系统提示词加载；`references/` 由模型按需读取，以控制上下文占用。

## 使用

技能在命中以下意图时自动触发，也可以显式点名：

```
使用 product-design-taste，审查这个项目的主流程、文案和视觉一致性，先给问题清单，不要改代码。
```

```
使用 product-design-taste 改善这个页面的设计品味，直接修改并用构建与关键交互验证，不要改变业务逻辑。
```

```
这个后台改了好几版还是不好看，用 product-design-taste 给三个方向让我选。
```

```
页面文案太像机翻了，按 product-design-taste 检查一遍本地化表达。
```

**典型触发语：** 提升产品设计品味、去掉 AI 味、这个页面不好看、检查产品是否易用、给三个设计方向、审查前端 UI、优化文案与数字展示。

## 目录结构

```
product-design-taste/
├── SKILL.md                              # 核心：工作流、判断顺序、优先级、交付规范
├── references/
│   ├── design-checklist.md               # 11 条原则的检查方法、修复建议与例外
│   └── acceptance-and-output.md          # 验证矩阵、输出模板、7 个行为验收案例
├── README.md
└── LICENSE
```

**渐进式加载设计：** `SKILL.md` 保持精简，常驻上下文；详细检查项与模板放在 `references/`，仅在执行到对应阶段时读取，避免一次塞满上下文窗口。

## 验证与交付

技能内置一张验证矩阵，覆盖主任务、异常状态、数据口径、响应式、多语言、无障碍、主题、工程构建与回归。样本视口为 360 / 768 / 1440 CSS px，多语言用 1.5–2 倍长度的伪本地化做布局压力测试。

交付物为结构化表格，三选一：

| 任务类型 | 输出 |
| --- | --- |
| 审查 | 问题与证据表（优先级 / 页面 / 证据 / 用户影响 / 修复 / 验收） |
| 实际修改 | 修改与验证表（文件 / 改动 / 目的 / 验证方法 / 实际结果） |
| 方向探索 | 三方向对比表（结构差异 / 适用场景 / 收益 / 成本 / 保留项） |

`references/acceptance-and-output.md` 还包含 7 个行为验收案例（A–G），覆盖只有截图、改现有产品、品牌冲突、数据与确认边界、长译文溢出、多轮不满意、过度极简等边界场景。

## 已知限制

- 行为验收案例是**规格**，不是已通过的真实产品测试结果。
- 没有浏览器或运行环境时，动态交互、渲染尺寸与辅助技术体验会明确标为未验证。
- 不替代用户研究与可用性测试：模拟走查不能证明真实用户能完成主任务。
- 默认审美（暖灰、单强调色、扁平）是起点而非标准答案；不同业务可覆盖，但需记录理由。
